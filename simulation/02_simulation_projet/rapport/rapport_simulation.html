Surveillance d'une ligne de production : simulation TinyOS / Cooja

Dix cartes simulées aux positions exactes du plan d'implantation, un réseau radio multi-saut (CTP), des capteurs de température, de comptage et de présence, et une passerelle qui produit les messages MQTT du cahier des charges. Chaque exigence vérifiable a son test automatique ; toutes les valeurs de ce rapport sont extraites des journaux de ces tests. Parmi les exigences non fonctionnelles, le groupe retient les trois plus simples à vérifier : ENF1 (latence < 10 s), ENF6 (messages authentifiés) et ENF8 (un nœud défaillant peut être retiré sans arrêter le reste).

1. Objectifs et correspondance réel ↔ simulation

Le système réel (architecture du groupe) repose sur des ESP32 en WiFi et un Raspberry Pi (Mosquitto, Node-RED, InfluxDB, Grafana). Cooja n'émule ni l'ESP32 ni le WiFi : il émule, instruction par instruction, des cartes de réseau de capteurs. On garde donc ce qui fait la difficulté du projet — la géographie de l'usine, les rôles, les exigences temporelles — et on remplace le matériel par son équivalent « réseau de capteurs ».

Limites de la correspondance. Les latences mesurées sont celles d'un réseau 802.15.4 non chargé, sans le trajet passerelle → broker → Node-RED → notification (budget < 3 + 3 + 2 s dans ENF1, non simulé). Le modèle UDGM est idéal (disque de portée, pas d'obstacle ni d'évanouissement) ; le test T6b le dégrade volontairement. Les capteurs sont simulés : la précision de ± 1 °C (EF1) dépend du composant réel (DS18B20 : ± 0,5 °C), pas du réseau.

2. Architecture de la simulation

2.1 Quatre rôles, quatre programmes

Une application nesC par rôle, avec un dossier commun/ partagé. Cooja charge donc quatre « types de cartes » ; chaque carte connaît son numéro (TOS_NODE_ID, écrit par Cooja) et en déduit, grâce à Plan.h généré depuis le plan, son repère, sa machine et son seuil.

NœudsProgrammeCe qu'il fait
1 (GW)passerelleRacine CTP ; vérifie l'authentification ; écrit topic + JSON ; alertes ; statistiques
2–4 (T1–T3)thermiqueLecture toutes les 2 s, rapport toutes les 30 s, alerte immédiate au-delà du seuil de SA machine
5–7 (C1–C3)comptage+1 à chaque pièce (sauvegarde en flash), rapport toutes les 30 s : cumul + cadence
8–10 (P1–P3)intrusionSuit l'heure de l'usine ; de nuit, toute présence → alerte immédiate + buzzer ; rapport de vie toutes les 30 s

2.2 Le message radio

Le JSON du cahier des charges est trop gros et trop coûteux à émettre sur une radio basse consommation. Les capteurs envoient une structure binaire de 22 octets ; c'est la passerelle qui fabrique le JSON. Un exemple de ligne réellement écrite par la passerelle (test T6) :

RX src=4 seq=1 sauts=1 parent=1 age=4 | factory/machines/MACHINE_03 {"node_id":"MACHINE_03","timestamp":1792512014,"temperature_c":73.0,"production_count":2,"status":"OK"}
ChampTailleContenu
type, etat1 + 1 octettempérature / comptage / présence ; OK, ALERTE, FIN_ALERTE, VEILLE, ARME, INTRUSION
source, seq2 + 2numéro du nœud et numéro de rapport (sert au taux de livraison et à repérer les doublons)
age_ms4temps passé dans le tampon : la passerelle en déduit l'horodatage réel de la mesure
valeur, compteur2 + 4dixièmes de °C · cadence et cumul de pièces · heure d'usine et nombre de détections
parent, etx2 + 2le premier relais et le coût de route CTP : permet de dessiner l'arbre
mac2code d'authentification calculé avec la clé du réseau (ENF6)

2.3 Routage multi-saut (CTP)

capteur ──PUB──> tampon ──CTP (saut par saut, accusé radio à chaque saut)──> passerelle ──> ligne MQTT

CTP (Collection Tree Protocol, tos/lib/net/ctp) construit seul un arbre dont la passerelle est la racine. Chaque nœud estime la qualité de ses liens (ETX : nombre moyen d'émissions pour réussir un envoi) et choisit le voisin qui minimise le coût total jusqu'à la racine. À 20 m de portée, P1 (22,7 m), P2 (26,2 m) et P3 (20,8 m) ne voient pas la passerelle : leurs rapports passent par un relais.

3. Le code, pas à pas

TinyOS est piloté par des événements : pas de boucle infinie, on écrit ce qu'il faut faire quand « la carte a démarré », « la minuterie a sonné », « un paquet est arrivé ». Un composant nesC a deux fichiers : une configuration (le câblage, avec des flèches ->) et un module (le comportement).

3.1 Câbler une application : le nœud thermique

configuration ThermiqueAppC {}
implementation {
  components MainC, LedsC, RandomC, ConsoleC, PublicationC;
  components ThermiqueC as App;
  components new TimerMilliC() as Lecture;
  components new TimerMilliC() as Rapport;

  App.Boot        -> MainC;
  App.Leds        -> LedsC;
  App.Random      -> RandomC;
  App.Console     -> ConsoleC;
  App.Publication -> PublicationC;
  App.Lecture     -> Lecture;
  App.Rapport     -> Rapport;
}

3.2 Lire le capteur et alerter tout de suite

  event void Lecture.fired() {
    if (surchauffe) {
      temp = seuil + 50 + aleatoire(3);        /* la sonde lit seuil + 5 °C */
    } else {
      derive += aleatoire(2);
      if (derive > 30) derive = 30;
      if (derive < -30) derive = -30;
      temp += (consigne + derive - temp) / 20;
      temp += aleatoire(3);                    /* bruit ±0,3 °C */
    }

    if (temp > seuil && !enAlerte) {
      enAlerte = TRUE;
      call Leds.led2On();                      /* LED bleue = machine en alerte */
      call Console.texte("DEPASSEMENT temp="); call Console.dixiemes(temp);
      call Console.texte(" seuil=");           call Console.dixiemes(seuil);
      call Console.car('\n');
      call Publication.publier(TYPE_TEMPERATURE, ETAT_ALERTE, temp, 0);
    } else if (enAlerte && temp <= seuil - HYSTERESIS_DIXIEMES) {
      enAlerte = FALSE;
      call Leds.led2Off();
      call Console.texte("RETOUR_NORMAL temp="); call Console.dixiemes(temp);
      call Console.car('\n');
      call Publication.publier(TYPE_TEMPERATURE, ETAT_FIN_ALERTE, temp, 0);
    }
  }

  /* --------------------------------------------------------------- rapport périodique */

commun/PublicationP.nc, ligne 120

Un rapport ne quitte le tampon que lorsque CTP confirme l'envoi. Si le relais est tombé, CTP finit par renoncer (échec) : le rapport reste en tête du tampon et repart 2 s plus tard, par la nouvelle route.

3.5 Le compteur qui survit au redémarrage

    /* IMPORTANT : pendant l'effacement et l'écriture, le contrôleur de flash bloque le CPU.
       Une interruption à ce moment fait planter le MSP430 (mspsim le reproduit :
       « Got interrupt while flash controller blocks CPU »). Le module d'origine servait
       au chargeur d'amorçage, sans interruptions ; ici on les MASQUE avec atomic. */
    atomic {
      FCTL2 = FWKEY + FSSEL1 + FN2;     /* horloge du contrôleur de flash */
      FCTL3 = FWKEY;                    /* déverrouillage */
      FCTL1 = FWKEY + ERASE;            /* effacement du segment de destination */

commun/FlashInterneC.nc, ligne 49

Le compteur est écrit dans la mémoire flash interne du MSP430 à chaque pièce, et relu au démarrage. mspsim reproduit fidèlement une contrainte du vrai matériel : une interruption pendant l'écriture fait planter le microcontrôleur. D'où le bloc atomic.

La latence mesurée inclut l'écriture de la ligne JSON sur le port série de la passerelle (≈ 11 ms à 115 200 bit/s) : la part radio est encore plus faible. On est très loin du budget de 1 s du cahier pour le trajet nœud → passerelle.

Dans cet essai, chaque nœud à portée du puits lui parle directement, et seuls P1, P2 et P3 passent par un relais. CTP choisit ses routes au démarrage d'après la qualité mesurée des liens et ne change de parent que si le gain dépasse un seuil (hystérésis) : selon les premiers paquets perdus, un nœud proche peut parfois rester sur un relais (observé lors d'essais précédents).

5.2 Alertes de surchauffe (T2)

De la mise à 95 °C à la ligne ALERTE SURCHAUFFE MACHINE_02 : 0,87 s, dont 39 ms entre la détection sur le nœud et l'alerte — le reste est l'attente de la lecture suivante (au plus 2 s). Cible de 5 s tenue.

5.3 Comptage et intrusion (T4, T5)

T4 : après 100 pièces, le compteur local vaut 100 et la passerelle publie "production_count":100. Le nœud C2, redémarré par son chien de garde à 42 pièces, relit 42 dans sa flash ; la passerelle détecte le redémarrage (numéro de rapport revenu à 1).

T5 : de nuit, l'alerte arrive en 47, 47 et 49 ms pour les zones 1, 2 et 3 (deux sauts chacune), avec le buzzer local. Les présences à 17h30 et à 08h30 ne déclenchent aucune alerte.

CTP ne détecte la panne qu'en essayant d'envoyer : P1 découvre l'absence de T1 à son rapport suivant, épuise ses retransmissions, puis change de parent. Le rapport retardé n'est pas perdu : il reste dans le tampon et repart par la nouvelle route.

5.5 Authentification (ENF6)

Les 10 rapports de l'intrus (même programme, autre clé) sont tous rejetés (REJET_AUTH), et aucun rapport légitime ne l'est. Le code d'authentification est calculé par le capteur et vérifié par la passerelle : un relais ne peut pas modifier un rapport sans être détecté.

7. Limites et perspectives

  • Prototype réel ESP32 + MQTT. Les lignes de la passerelle contiennent déjà le topic et le JSON : un pont série → mosquitto_pub suffit pour alimenter Node-RED, InfluxDB et Grafana. En WiFi, CTP disparaît (le point d'accès joue la racine).
  • Sécurité. Le code d'authentification sur 16 bits est pédagogique (FNV-1a « salé »), sans protection contre le rejeu ni chiffrement. En réel : AES-CCM matériel du CC2420 (802.15.4) ou TLS sur MQTT (port 8883) avec un certificat par ESP32, et un compteur anti-rejeu.
  • Heure d'usine. Chaque nœud la calcule depuis son démarrage (écart ≤ 1 s entre nœuds dans Cooja). En réel : NTP sur l'ESP32.
  • Modèle radio. UDGM est un disque parfait. Une étude plus réaliste utiliserait le modèle MRM ou DGRM de Cooja avec les murs du plan.
